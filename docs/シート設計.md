# スプレッドシート設計

最終更新: 2026-08-19

対象スプレッドシート: 見積もりフォームの回答が蓄積されている既存シート
（ID はスクリプトのプロパティ `BOARD_SPREADSHEET_ID` ではなく、バインド先として自動解決）

**このファイルはシート構造を変更するたびに必ず更新する。**

---

## タブ一覧

| タブ | 役割 | 作成元 |
|---|---|---|
| 案件ボード | 進行中の案件一覧。ここだけ見れば回る | 新規 |
| 顧客 | 顧客マスタ。請求・返送に必要な情報を保持 | 新規 |
| メール履歴 | 届いたメールと、それに対する返信文面の記録（②で使用） | 新規 |
| テンプレ | メール文面 T1〜T7 | 新規 |
| ナレッジ | 回答方針メモ・返信実例（②で使用） | 新規 |
| 設定 | 発送先・通知先などの値 | 新規 |
| ログ | 実行履歴 | 新規 |
| `Config` | **既存。見積もりフォームの設定JSON。変更禁止** | 既存（非表示） |
| `Responses` | **既存。フォーム回答の生データ。変更禁止・読み取りのみ** | 既存（非表示） |

既存2タブはフォームが読み書きしているため一切変更しない。
案件・顧客の行は `Responses` を**読み取って**生成する。

## 案件ボード

1行＝1案件。左から4列を固定表示し、見出し行に絞り込みを付けている。

**列の位置は書かない。** 手で並べ替えられる前提のため、見出し名で管理する。

| 項目 | 種別 |
|---|---|
| 案件ID | 自動（`A001`〜） |
| ステータス | プルダウン。**色は付けない** |
| 対応者 | **数式で自動表示**。自分 / お客様 / 完了。**色は付けない** |
| お客様 | 自動（顧客タブから） |
| 予定点数 | 任意入力。空欄なら案内メールの点数行が自動で消える |
| 初回ご依頼予定数 | 自動。見積もり回答へのご返信から取り込む |
| 初回ご依頼予定日 | 自動。同上。受付開始日の初期値になる |
| 受付開始日 | **★手入力必須** |
| 納期予定（自） | **★手入力必須** |
| 納期予定（至） | 任意。入れると「◯月◯日 〜 ◯月◯日」と範囲で案内する |
| 次にやること | **数式で自動表示** |
| 未返信 | **数式で自動表示**。対応中のメール件数。クリックでメール履歴へ飛ぶ。ある行は薄いアンバーで色が付く |
| 顧客ID | 自動 |
| 依頼内容 | 自動（フォームで選ばれたプラン内容） |
| フォームの問い合わせ内容 | 自動。フォーム回答の記入内容。**あとから変わらない** |
| 最新の受信メール | 自動。最後に届いたメールの日時と本文 |
| 最新の送信メール | 自動。最後に送ったメールの日時と本文 |
| 単価 | 自動（フォーム回答） |
| 請求書送付日 | 自動（Square請求書の送信確認時） |
| Square請求書ID | 自動（請求書の下書き作成時、または顧客から検索して紐づけ） |
| 署名・支払確認日 | 自動（支払いと署名がそろったとき）／手入力 |
| 追跡番号 | 自動（発送メールから読み取り）／手入力 |
| 作業チーム共有 | 自動（発送を検知したときにまとめる） |
| 案内メール作成日 | 自動（下書き作成時） |
| 最終連絡日 | 自動 |
| メモ | 手入力 |
| 元回答行 | 自動（`Responses` の行番号。重複取込の防止） |

3つの内容を別の列に分けている。

| 列 | 中身 | 変化 |
|---|---|---|
| 依頼内容 | 撮影・クリーニングなど**選ばれたプラン** | フォーム回答時のまま |
| フォームの問い合わせ内容 | フォームで**お客様が書いた文章** | フォーム回答時のまま |
| 最新の受信メール | **最後に届いたメールの日時と本文** | メールが届くたび更新 |
| 最新の送信メール | **最後に送ったメールの日時と本文** | メールを送るたび更新 |

どちらの文章列も400文字を超えると切り詰め、全文はメール履歴の `受信本文` 列に残る。
過去のやりとりは「対応を選ぶ」画面の「過去のやりとり」で読める。

### 未返信の見分け方

**「未返信」列と行の色でだけ知らせる。** ステータスと対応者には色を付けない。

- 「未返信」は**スクリプトが書き込む**（`boardRefreshUnreplied_`）。
  その顧客IDのメール履歴の行のうち、状態が `返信前` のものを数え、`● 2件` のように出す
- **1通ずつ別のリンクにする。** 受信日（`8/18 ・ 8/19`）を新しい順に並べ、それぞれメール履歴の該当行へ飛ぶ。
  5通以上あるときは新しい4通だけ出し、残りは `+3` とまとめる（`BOARD_UNREPLIED_MAX_LINKS`）
- ステータスが `見送り` `返送済` の案件には出さない。「対応を選ぶ」の一覧と同じ扱い

> **ここは数式にしない。**
> 件数と飛び先の行を1つの数式で求めようとしたが、開いた範囲（`A2:A`）の長さの扱いが
> スプレッドシート側の判断に左右され、件数が0になったり飛び先が別の行になったりした。
> メール履歴を読んで数えるだけなので、スクリプトで計算して書くほうが確実。
>
> メール履歴に動きがあるところから毎回呼ぶ。呼び出し元は
> 初期セットアップ／新着チェック（`mailScan_`）／「対応を選ぶ」の一覧読み込み／対応不要のチェック。
> 10分ごとの自動チェックでも通るため、ずれても次の実行で直る。
- **1件でもあれば、その案件の行全体が薄いアンバー（`#FDF3E3`）になる**（条件付き書式）
- 下書きを実際に送れば状態が `返信済み` に変わり、色は自動で消える

**返信が要らないメール**（2通続けて届いた場合など）は、飛んだ先のメール履歴で
**状態を `対応不要` に変える**。戻したいときは `返信前` に戻す。

状態を手で変えると、案件ボードの未返信もその場で更新される（`boardOnEditInstalled_`）。
これは**インストール型のトリガー**で動く。初期セットアップが1つだけ登録する。
簡易トリガーの `onEdit` は権限が限られていて静かに失敗することがあるため使わない。

> **対応不要のチェックボックス列は置かない。**
> 状態列と同じことを二重に持つと、両方を合わせる処理が要るうえ、食い違いの原因になる。

### 一覧としての見やすさ

長い文章が入る列（依頼内容・フォームの問い合わせ内容・最新の受信メール・最新の送信メール・作業チーム共有・メモ）は
**折り返さず1行に収める**（クリップ表示）。行の高さは `setRowHeightsForced` で50pxに固定するため、案件が縦に伸びない。
（`setRowHeights` では「データに合わせる」の指定が残り、自動調整の行だけ伸びたままになる）
中身の全文はセルを選べば数式バーで読め、「対応を選ぶ」画面でも読める。

**普段見ない詳細列は折りたたみグループにまとめる**（`boardApplyGroups_`）。
見出しの上に出る ＋／− で開閉できる。対象は `BOARD_DETAIL_COLS`
（初回ご依頼予定数・初回ご依頼予定日・顧客ID・依頼内容・フォームの問い合わせ内容・単価・
請求書送付日・Square請求書ID・署名・支払確認日・作業チーム共有・案内メール作成日・
最終連絡日・メモ・元回答行）。

グループは位置でしか作れないため、**いま隣り合っている詳細列の範囲ごとに**作る。
列を並べ替えたあとに初期セットアップを実行すれば、新しい並びで作り直される。
初期セットアップのたびに折りたたまれた状態に戻る。

### 列の並べ替え

**案件ボードの列は手で並べ替えてよい。**
コードは実行のたびに1行目の見出しを読み、列番号を実際の並びに合わせる（`boardSyncColumns_`）。
初期セットアップも、見出しが揃っていれば並び順を書き戻さない。

ただし**見出しの文字を変えたり、列を消したりしない**こと。
見出しが1つでも欠けると古い構成とみなされ、移行処理が走る。
幅と固定列は既定値を持つが、手で変えたものはセットアップで上書きされる場合がある。

### 受信・送信メールの更新（`boardRefreshInquiries_`）

**新着メールの読み取りとは切り離してある。** あちらは記録済みのメールを二度と読まないため、
そこに相乗りさせると既存のメールがいつまでも反映されない。

- 顧客タブのアドレス（最大30件）を `{from:a from:b …}` の形で**まとめて1回だけGmail検索**する
- 受信は `{from:a from:b …}`、送信は `in:sent {to:a to:b …}` の形でそれぞれ1回検索する
- 顧客ごとに**最後の1通**を選び、日時と引用を除いた本文を書き込む
- `最終連絡日` は、受信と送信のうち新しいほうに合わせる
- メールが1通も無い案件は、フォームの「お問い合わせ内容・補足」で埋める
- 内容が変わっていない行は書き込まない

自動確認と「新着を今すぐ確認する」の両方で実行する。

## 顧客

1行＝1顧客。**キーはメールアドレス**。同じアドレスからの再問い合わせは既存行を更新する。
Square の請求書作成と返送に必要な情報を保持し、一覧で確認・修正できる。

| 列 | 項目 | 種別 |
|---|---|---|
| A | 顧客ID | 自動（`C001`〜） |
| B | 会社名・屋号 | フォーム／**お客様の返信から自動** |
| C | 担当者名 | フォームから自動／修正可 |
| D | メールアドレス | フォームから自動（**キー**） |
| E | 電話番号 | フォームから自動／修正可 |
| F | ストア名 | **お客様の返信から自動** |
| G | 代表者名義 | **お客様の返信から自動** |
| H | 請求先 郵便番号 | **お客様の返信から自動** |
| I | 請求先 住所 | **お客様の返信から自動** |
| J | 返送先 郵便番号 | **お客様の返信から自動** |
| K | 返送先 住所 | **お客様の返信から自動** |
| L | 返送先 宛名 | **お客様の返信から自動** |
| M | 返送先 電話番号 | **お客様の返信から自動** |
| N | 依頼内容 | フォームから自動／修正可 |
| O | 月間予定数 | フォームから自動 |
| P | 単価 | フォームから自動／修正可 |
| Q | 初回問い合わせ日 | 自動 |
| R | 最終更新日 | 自動 |
| S | メモ | 手入力 |
| T | Square顧客ID | 請求書作成時に自動 |

Square の請求書送付に**必須なのはメールアドレスだけ**（公式ドキュメントで確認済み）。
氏名・会社名・電話番号・住所はいずれも任意で、姓名を分ける必要もない。
会社名や氏名は請求書と契約書の宛名として使うため、実務上は入れておく。

### お客様の返信からの自動取り込み

見積もり回答（T1）で下記の見出しを送り、返信に同じ見出しがあれば該当列へ書き込む。
定義は `BOARD_CUSTOMER_INTAKE`（board.js）。

`ストア名` / `会社名` / `代表者名義` / `請求先郵便番号` / `請求先住所` /
`返送先郵便番号` / `返送先住所` / `返送先電話番号` / `宛名`

`初回ご依頼予定数` と `初回ご依頼予定日` は顧客ではなく**案件**に保管する（`BOARD_CASE_INTAKE`）。
「対応を選ぶ」→「依頼確定」で、予定点数と受付開始日が未入力のときの初期値になる。

| 項目 | 読み取れる書き方 |
|---|---|
| 初回ご依頼予定数 | 50点／約50／１００点 |
| 初回ご依頼予定日 | 2026年9月1日／2026/9/1／9/1／１２月３日 |

日が定まらない書き方（9月上旬・未定など）は読み取らず、空欄のままにする。

- 見出しは全角・半角どちらのコロンでもよく、行頭の `・` や引用記号 `>` は無視する。
- **コロンを付け忘れた行も拾う**（`返送先郵便番号 2360031` のように、見出しのあと空白で値が続く形）。
  拾うのは**見出しが完全に一致する行だけ**なので、ふつうの文章を取り違えることはない。
  実際に、1行だけコロンが抜けていて返送先郵便番号が取り込めず、案件が「情報不足」から動かなくなった。
- 括弧書きの補足（例：`会社名（個人事業主の方は個人名義）`）は取り除いて照合する。
- **値が空の行は無視する**ため、引用された空欄のテンプレートで既存の値が消えることはない。
- 既存の値と違う場合は上書きし、更新した項目名をログに残す。

取り込みは**新着を記録したときにしか走らない**。読み取りの条件を直しても、すでに記録された
メールには反映されないため、初期セットアップで受信本文を見直す（`boardBackfillIntake_`）。
**このときは空欄だけを埋め、手で直した値は上書きしない。**

> **顧客情報の補完は、ステータスの見直しより先に行う。**
> 逆にすると、情報がそろっているのに `情報不足` のまま残る。実際にそうなった。

ステータスの見直し（`boardReevaluateStatuses_`）は、初期セットアップだけでなく
**新着チェックでも毎回走る**。取り込みは新着のときしか動かないため、
あとから顧客情報が埋まった案件を10分以内に拾い直せるようにしてある。

## メール履歴（②で使用）

**1行＝お客様から届いたメール1通**（＋フォーム回答）。**こちらが送ったメールの行は作らない。**
1通の受信メールと、それに対するこちらの返信を、同じ行の左右に置く構成。

| 列 | 項目 | 表示 |
|---|---|---|
| A | 日時（**メールが届いた日時**。フォーム回答の行は記録した日時） | 常時 |
| B | 顧客ID | 常時 |
| C | お客様（顧客タブから引く数式） | 常時 |
| D | 差出人 | 常時 |
| E | 件名 | 常時 |
| F | **受信本文**（`受信日時` の行＋届いたメールの本文。4000文字まで） | 常時 |
| G | AI初回案（生成直後の文面。学習の比較元） | 折りたたみ |
| H | 修正指示ログ（AIへの指示を時刻付きで蓄積） | 折りたたみ |
| I | **返信文面**（`返信日時` の行＋こちらが返す文面。編集・修正後の現在の内容） | 常時 |
| J | **状態**（プルダウン。対応不要にするのもここ） | 常時 |
| K | GmailスレッドID | 折りたたみ |
| L | 下書き保存日時 | 折りたたみ |
| M | 対応種別（どの状況での回答か） | 常時 |
| N | 下書きID（作り直すときに前の下書きを消すために保持） | 折りたたみ |
| O | GmailメッセージID（**同じメールを二度記録しないための目印**） | 折りたたみ |

スレッド単位ではないため、同じスレッドに届いた2通目以降も1行ずつ増える。

**同じ通かどうかは GmailメッセージID で見分ける**（`boardDedupeMails_`）。
顧客・件名・スレッドで見ると、同じスレッドに届いた別のメールまで重複とみなして消してしまい、
次の新着チェックで作り直される堂々巡りになる。

### 本文の先頭に付く日時

受信本文と返信文面は、**1行目に日時、2行目から本文**という形で持つ。
同じスレッドのメールは件名で見分けられないため、シート上で区別できるようにしている。

**この1行はメールの中身ではない。**
画面へ渡すときと Gmail の下書きを作るときは `mailUnstamp_` で必ず外す。
外し忘れると、日時の行がそのままお客様へ送られてしまう。
付け直しは `mailStamp_` が古い日時を取り除いてから行うので、重ねても増えない。

### 状態

**「そのメールに、こちらがどこまで返したか」を表す。Gmailの開封状況とは関係ない。**
プルダウンにしてあり、入力時に同じ説明が出る（`MAIL_STATUS_HELP`）。

| 状態 | 意味 |
|---|---|
| 返信前 | まだ返していない（返信案の作成中・下書き保存済みもここ） |
| 返信済み | 返信を送った |
| 対応不要 | 返信しないと決めた |

`返信前` だけが「対応中」（`MAIL_OPEN_STATUSES`）で、案件ボードの「未返信」に数えられる。
旧称（未確認／修正中／下書き保存済／下書きあり／返信案あり／送信済）は
初期セットアップで自動的に書き換わる（`MAIL_STATUS_RENAMES`）。

> **持つのは「送ったかどうか」だけ。**
> 途中の段階（返信案あり・下書きあり）は廃止した。
> 文面がどこまでできているかは画面を見れば分かり、状態として分けても次にやることは変わらない。
> 下書きに保存しても `返信前` のまま。実際に送った時点で `返信済み` になる。

> **「下書きあり」は廃止した。**
> Gmailの下書きにしたかどうかは、画面に文面がある状態と見分けが付かず、
> 分けても次の判断の助けにならなかった。文面ができていれば `返信案あり` の1つにまとめる。

### 確認しやすいレイアウト（`boardApplyMailFormatting_`）

- **並べ替えはしない。** 記録した順に下へ足していく。お客様ごとや日付順に見たいときは、見出しの絞り込みから手で並べ替える
- 行の高さは**50pxで固定**。長文の列は折り返さない
- 1行目と左3列（日時・顧客ID・お客様）を固定表示
- **文面そのもの（受信本文・返信文面）は折りたたまない。** 畳むのは内部用の列だけ（`BOARD_MAIL_DETAIL_COLS`）
- **対応中のメール**の行は、案件ボードと同じ薄いアンバーになる

### 送信済みの検知

`返信前` の行について、実際に送られたかを Gmail 側で確かめる。**行の作られ方で見る場所が違う。**

**メールから作られた行**（`mailRefreshSentStatus_`）
スレッドをたどり、最新のメールが自分から送られていれば `返信済み`。
ただし最新が下書きなら進めない（下書きもスレッドの一員として返ってくる）。

**フォームの回答から作られた行**（`mailSyncSentReplies_` → `mailFirstSentAfter_`）
届いたのはメールではないためスレッドが無く、**こちらの返信も「返信」ではなく新規メール**として送っている。
そのため**送信済みフォルダ**から、そのお客様宛で回答日時より後に送った最初のメールを探す。
見つかればその本文を `返信文面` に入れ、`返信済み` にする。

> **下書きが残っているかどうかでは判断しない。**
> Gmailで直接書いて送った場合、こちらが作った下書きは残ったままになり、
> いつまでも `返信前` から進まなくなる。実際にそうなった。
>
> 逆に「そのお客様へ送った別件のメール」を返信とみなす可能性はある。
> 何を返信とみなしたかは `返信文面` に入るので、見れば分かるようにしてある。

### 返信文面の照合（`mailSyncSentReplies_`）

**その受信メールの次にこちらが送ったメールを、同じスレッドから探して返信文面に入れる。**
Gmailから直接返信した場合も記録に載る。作りかけ（返信案あり・下書きあり）と対応不要の行には触らない。

1スレッド1行だった頃、画面には常に最新の受信メールが出ていたため、
その返信が別の受信メールの行に保存されていた。その食い違いもここで直る。

## 返信実例（②の学習用）

承認して下書きに保存した時点で1行追加される。

| 列 | 項目 |
|---|---|
| A | 日時 |
| B | 顧客 |
| C | 件名 |
| D | AI初回案 |
| E | 修正指示 |
| F | 最終文面 |
| G | 抽出した方針 |

G列は、初回案と最終文面に差があるとき、AIが「次回に活かせる行動指針」を1〜2行で抽出したもの。
抽出結果はナレッジタブへ `学習（要確認）` として自動追記される。

> **学習がテンプレを書き換えることはない。**
> 学習の書き込み先は「返信実例」と「ナレッジ」の2つだけで、テンプレシートには一切触れない。
> テンプレを変更するのは、人の手による編集と、初期セットアップ時の移行処理のみ。
> また T1〜T7 の定型文はテンプレをそのまま差し込むだけでAIを通さないため、
> 学習の内容によって文面が変わることもない。AIが関わるのは「通常の返信」だけ。
**誤った学習が入る可能性があるため、ナレッジタブの「学習（要確認）」行は定期的に目視し、
不要なら削除・修正する。**

### 差し込み変数のうち、条件付きで消える行

| 変数 | 消える条件 |
|---|---|
| `{{予定点数}}` | 予定点数が空欄のとき、その行ごと削除 |

## ② メール返信支援（mail.js）

```
10分ごとのトリガー（Google のサーバー上で実行。PCの電源は不要）
  ├ Responses の未取込行から顧客・案件を作成
  └ 顧客タブのアドレスごとに Gmail を検索
      条件: 直近30日
      └ 見つかったスレッドの中の、**お客様から届いたメールを1通ずつ**見る
            ├ メール履歴に同じ GmailメッセージID があれば飛ばす（記録済み）
            ├ 請求先・返送先の記載があれば顧客タブへ取り込む
            ├ メール履歴タブに「返信前」として1行追加（本文をそのまま受信本文欄へ）
            └ 24時間以内に届いたものだけ、通知先アドレスへ
               「届いたメールの中身＋シートへのリンク」をメール送信
```

**検知の時点では返信案を作らない（Claude API を呼ばない）。**
返信案は「対応を選ぶ」で対応種別を選び、［この対応で返信案を作る］を押したときだけ作る。
どのテンプレートで返すかは人が決めるため、先に案を作っても作り直しになるだけで、費用も無駄になる。

### フォーム回答も対応リストに載る

見積もりフォームに回答があった時点で、メール履歴へ「返信前」の行を1件作る。
**お客様からメールが届くのを待たないため、初回の返信が漏れない。**

- 対応種別は未選択。受信本文欄にフォームの問い合わせ内容と選択内容が入る。
- GmailスレッドIDは空。承認時は返信ではなく**新規メールの下書き**を作る。
  件名は対応種別のテンプレートのものを使う。
- この行の作成時点ではAIを呼ばない（費用ゼロ）。

**手動実行（新着を今すぐ確認する）は通知メールを送らない。**
画面を見ている前提のため、結果はダイアログに出したうえで「対応を選ぶ」画面を開く。

### 確認画面（メニュー「対応を選ぶ」）

モーダルダイアログで開く。左に確認待ちの一覧、右に対応種別・本文編集欄。

一覧の1件は上から **お客様名（案件ボードの「お客様」列）／メールアドレス／件名／日時と状態** の4行。
お客様名が空のときはメールアドレスを代わりに出す。

**進行中の案件があるお客様は、返信待ちが無くても全員出す。**
こちらから続けて連絡する用があるため、一覧に居ないと開けないから。
出さないのはステータスが `見送り` `返送済` の案件だけ（`BOARD_FINISHED_STATUSES`）。

お客様1人につき1件。**返信待ちの行を優先し、その中では新しいもの**を選ぶ。
返信待ちが1つも無ければ、いちばん新しい行を選ぶ。並び順は返信待ちが上、そのあとは新しい順。

**「お客様のメール」欄には、その行そのものの内容を出す。**
GmailメッセージIDがあればそのメールを Gmail から読み、無ければ（フォーム回答の行）
シートの `受信本文` を「フォームからの回答」として出す。

> お客様単位で最新のメールを探す作りにしていた時期があるが、それでは
> **フォーム回答の行を選んでも、別のメールが表示されてしまう**。
> 1行＝メール1通になった今は、その行の内容を出すのが正しい。

**「過去のやりとり」を開くと、送受信を新しい順に並べて全文が読める。** 主に Gmail から組み立て、
**フォームの回答（Gmailに存在しない）はメール履歴から拾って「フォーム」として混ぜる**。
こちらから送ったメールはシートに残らないため、Gmail が唯一の全体像になる。さかのぼる期間は180日。

| 操作 | 動作 |
|---|---|
| どの状況での対応か | 対応種別を選ぶ（初期は未選択）。選ぶだけでは文面は変わらない |
| この対応で返信案を作る | テンプレートと問い合わせ内容をもとに、AIが返信案を作る |
| 本文を直接編集 | テキストエリアでそのまま書き換えられる |
| AIに修正を依頼 | 指示文を入れて実行。指示は修正指示ログへ蓄積される |
| 最初から作り直す | AIに再生成させる。過去の修正指示は引き継ぐ。状態は「返信前」に戻る |
| この内容で下書きに保存 | Gmailの同スレッドに下書きを作成し、案件ステータスを更新。返信実例へ記録・方針を抽出。**前の下書きは削除して作り直す** |
| 編集内容だけ保存 | シートにだけ保存（下書きは作らない） |
| 対応不要 | 一覧から外す |

### 差し込みで埋まらない箇所

テンプレートに `【ここに…】` と書いた箇所は、**人が書き換えないと下書きにできない**
（`BOARD_TEMPLATE_PLACEHOLDER`）。納品データのURLのように、こちらの判断でしか入らない値に使う。
残ったまま［この内容で下書きに保存］を押すと、何が残っているかを添えて止める。

### 対応種別と、同時に必要な処理

`BOARD_RESPONSE_TYPES`（board.js）で定義。選ぶと画面に「同時に必要な処理」が表示され、
下書き保存時に案件ステータスが自動更新される。

初期状態は**未選択**。選ぶと、その対応に必要な入力欄と操作が**同じ画面に追加表示される**。
別のメニューへ移動する必要はない。

文面は選んだだけでは変わらない。**［この対応で返信案を作る］を押すと、
テンプレートを土台に、お客様の問い合わせ内容へ合わせた返信案をAIが作る。**
テンプレートの料金・納期・住所などは一字一句そのまま残すよう指示している。
「通常の返信」を選んだ場合はテンプレートを渡さず、方針と実例だけで書く。

| 対応種別（画面表示名） | 本文 | 案件ステータス | 追加で表示される操作 |
|---|---|---|---|
| 通常の返信（AIが問い合わせ内容に応じて回答します） | AI生成 | 返信済 | なし |
| 見積もり回答（料金・納期の目安・ご利用条件をお伝えします） | T1 | 返信済 | なし |
| 依頼確定（受付開始日・納期を回答し、依頼内容・支払い・発送に関する事項を伝えます） | T2 | 支払い情報登録・契約書署名待ち | 受付開始日**（必須）**／納期予定 自**（必須）**・至／予定点数 ＋ **初回登録の請求書の作成・送信** |
| 手続き完了（支払いと署名の確認をお伝えし、発送をご案内します） | T4 | 発送待ち | 署名・支払確認日 |
| 手続きの催促（支払い・署名がお済みでない方へご確認をお願いします） | T5 | 変更なし | なし |
| 発送の催促（発送状況の確認と、追跡番号のご連絡をお願いします） | T6 | 変更なし | なし |
| お預かり完了（商品の到着と点数をお知らせし、納期の目安を再度お伝えします） | T7 | 作業中 | 予定点数（実際の到着点数に更新） |

- 対応する案件は、そのお客様の最新の案件（返送済・見送りを除く）を自動で選ぶ。
- **必須の入力欄が埋まるまで「この内容で下書きに保存」は押せない。**
- 定義は `BOARD_RESPONSE_TYPES` と `BOARD_CASE_FIELDS`（board.js）。

- **下書きは承認したときにだけ作られる。** 自動では作らない。
- **自動送信は実装しない。**

### やり直したいとき

| 状況 | 対処 |
|---|---|
| Gmailの下書きを消してしまった | 一覧に残っているので、そのまま「この内容で下書きに保存」を押し直す |
| 返信案そのものを作り直したい | 「最初から作り直す」を押す |
| 一覧から消えている（返信済み／対応不要） | メール履歴タブの `状態` 列を手で `返信前` に戻すと一覧に戻る |

### 同じメールを二度拾わない仕組み

**メール1通ごとの GmailメッセージID で管理する。** メール履歴のN列に記録済みのIDが残り、
それと一致するメールは飛ばす。同じスレッドに届いた2通目・3通目もそれぞれ別の新着として扱う。

以前は Gmail ラベル `ササゲパス/返信案作成済` をスレッドに付けて管理していた。
ラベルはスレッド単位でしか付かないため、**一度やりとりしたお客様からの返信を取りこぼしていた。**
現在このラベルは使っていない（すでに付いているラベルは残しても支障ない）。

- 記録済みIDを持たない古い行には、`mailBackfillMessageIds_` が当時のメールのIDを補う。
  補わないと、過去に確認済みのメールがすべて新着として出てきてしまう。
- 過去分をまとめて取り込む場合に通知が溢れないよう、**通知は24時間以内に届いたものだけ**。
- 1回の実行で記録するメールは最大10通、検索するスレッドはお客様1人につき最大5件（暴走防止）。
- モデルは `claude-sonnet-5`。スレッド本文は直近4000文字までに制限。
- 料金・納期など方針に書かれていない情報は創作しないようシステムプロンプトで指示している。

**日常的に使うもの**

**設定（サブメニュー）**

| 項目 | 動作 |

### 登録手数料の請求内容

過去の請求書（`000014` / `000016` / `000022`）から抽出した実績値をそのまま使用する。

| 項目 | 値 |
|---|---|
| 店舗 | ササゲパス（`L11Z7FV5M0N4X`） / JPY |
| 品目 | 登録手数料 × 1 |
| 単価 | 200円（税抜） |
| 税 | 消費税 10.0%・ADDITIVE・LINE_ITEM → 合計220円 |
| タイトル | サービスご利用における決済情報のご登録とご署名に関するお願い |
| メッセージ | テンプレ `S1`（過去の文面と完全一致。空行・全角空白まで再現） |
| 送付方法 | EMAIL |
| 支払方法 | カードのみ（ギフトカード・銀行振込・後払い・Cash App はすべて無効） |
| カード情報の保存 | 有効（`store_payment_method_enabled: true`） |
| 支払期限 | 発行日の2日後 |
| チップ | 無効 / 自動支払い なし / リマインダー なし |

### 契約書は API から扱えない（確認済み）

Square の公開APIに **Contracts API は存在しない**。請求書の `attachments` は画像とPDFのファイル添付専用で、
電子署名付きの「Square 契約書」を添付する手段はない。契約書はダッシュボード専用機能である。

契約書の事前作成は不要。**請求書の編集画面でその場で新規作成して添付する**。
（添付ファイルとカスタムフィールド → Square 契約書 → 新規の契約書 → サービス利用規約 → 保存）

### 手続き画面（メニュー「Squareの手続きを進める」）

案件ボードで行を選んで開くモーダル。2段階を順に進め、完了した段階は緑で表示される。

| # | 内容 | 担当 | 記録先 |
|---|---|---|---|
| 1 | Square顧客の作成（既存があれば流用）＋ 請求書を DRAFT で作成 | **自動** | 顧客タブ `Square顧客ID` / 案件 `Square請求書ID` |
| 2 | 契約書を添付して送信 | 手動 | 案件 `請求書送付日` |

- 手順2の説明文は**設定タブの「請求書送信の手順」で編集できる**。
  Square の画面が変わったらここを書き換える。
- 手順2の「送信しました」は、**Square側の請求書状態を実際に確認**してから記録する。
  まだ DRAFT のままなら記録せずエラーを返すため、送信し忘れたまま先に進むことがない。
- 手順1が終わるまで手順2のボタンは押せない。

### 支払いと署名の完了確認（自動）

`squareCheckCompletions`（square.js）。自動確認と「新着を今すぐ確認する」の両方から実行する。
対象は**ステータスが「支払い情報登録・契約書署名待ち」かつ署名・支払確認日が空**の案件のみ。

| 確認したいこと | 方法 |
|---|---|
| 220円の支払い | Square APIで請求書のステータスを取得し `PAID` / `PARTIALLY_PAID` を判定 |
| 契約書への署名 | Square から届く署名完了メールをGmailで検索 |

案件に `Square請求書ID` が無い場合（Squareの画面で直接作った請求書など）は、
メールアドレスからSquareの顧客を探し、その顧客宛の登録手数料の請求書を検索して紐づける。
見つかったIDは案件へ書き戻すので、次回以降は検索しない。
それでも見つからない案件はログに理由を残す。

署名メールの判定条件:

- 差出人が `noreply@messaging.squareup.com`
- 件名に「署名されました」を含む
- 件名か本文に、**その顧客を見分ける文字列のいずれかを含む**

契約書はSquare上の顧客に対して発行されるため、業務ボードに登録した連絡先と
**メールアドレスが違うことがある**。そのため次を手がかりにする。

- 顧客タブのメールアドレスと担当者名
- Square側の顧客のメールアドレス・氏名・会社名（`Square顧客ID` からAPIで取得）

比較のときは空白を落とし、3文字未満の手がかりは使わない（取り違え防止）。

両方そろったときだけ次を行う。

- `署名・支払確認日` に署名日を記録し、ステータスを **発送待ち** へ進める
- **手続き完了のご連絡（T4）をお客様へ自動送信する**（設定で停止可）
- 送った内容はメール履歴へ「送信済」として残す
- 通知先アドレスへ結果を知らせる

> **このシステムで唯一、下書きを挟まずに自動送信する処理。**
> 文面は定型文をそのまま使い、AIは通さないため内容は毎回同じ。
> 止めたいときは設定タブの「手続き完了の自動送信」を「オフ」にする。

以前の記述:

- 案件ボードの「次にやること」が **「手続き完了のご連絡を送る」** に変わり赤字になる
- 通知先アドレスへ「手続き完了。発送のご案内を送ってください」とメールを送る

片方だけでは記録しない。支払いだけ済ませて署名を忘れる、あるいはその逆を見逃さないため。

## 発送の検知と作業チームへの共有（shipping.js）

`shipCheckAll`。自動確認と「新着を今すぐ確認する」の両方で実行する。
対象は**ステータスが「発送待ち」または「支払い情報登録・契約書署名待ち」**の案件。

```
その顧客からの最新メールを取得
  └ 前回と同じメールなら何もしない（同じ内容をAIに繰り返し読ませない）
      └ Claude が本文と添付画像を読み、次を判定
          shipped   発送されたか（発送予定・検討中は false）
          tracking  追跡番号（本文になければ送り状の写真から）
          quantity  発送された点数
          arrival   到着予定
          notes     作業上の特記事項
```

発送と判定されたときだけ、次を行う。

- `追跡番号` に番号を記録
- ステータスを **発送済み** に変更
- `作業チーム共有` 列に共有内容をまとめる
- 「次にやること」が **作業チームへ共有する** に変わり赤字になる

### 作業チーム共有の内容

**料金は載せない。** 依頼内容から `（¥400/点）` のような価格表記を取り除く。

```
【作業依頼】A005　古川 裕規

■ 追跡番号
　123456789012
　https://toi.kuronekoyamato.co.jp/cgi-bin/tneko?number=123456789012
　到着予定: 8月19日

■ 点数
　10点

■ 納期予定
　2026年8月25日 〜 2026年8月28日

■ 作業内容
　・クリーニング：スチームアイロン
　・クリーニング：簡易洗浄
　・撮影：白抜き・正方形撮影

■ お客様からの指定
　手を加えてほしくない商品はありません
```

送信はしない。この列をコピーして、任意の手段でチームへ渡す。

### 手続き完了の連絡について

支払いと署名がそろった時点で**ステータスを自動的に「発送待ち」へ進める**。
発送先は案内メール（T2）で伝え済みのため、完了の連絡は行わない。
対応種別の「手続き完了」は選択肢としては残すが、「次にやること」では促さない。
